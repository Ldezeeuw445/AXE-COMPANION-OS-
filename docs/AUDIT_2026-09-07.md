# AXE Companion — Launch Audit (2026-09-07)

Evidence-based audit of `www.axecompanion.com`. Every claim below was measured
against production, the live Supabase project (`pqnngpcgbdwxavbatbia`), the Railway
streamer, and a clean local build of `main`. Nothing here is inferred from the
existing checklist — several checklist rows turned out to be stale.

**Verdict: not launch ready.** Three blockers are critical (one is a live data
leak). The app shell, auth, gating and build are healthy; everything that runs
*behind* the app has been dead since mid-July.

---

## 1. Where production actually runs

`docs/LAUNCH_CHECKLIST.md` A2 and `AXE_SYSTEM_TRUTH.md` both say "Production is
live on Vercel". It is not.

```
$ getent hosts www.axecompanion.com
212.227.91.79
$ curl -I https://www.axecompanion.com/
server: nginx/1.24.0 (Ubuntu)
```

Vercel serves `server: Vercel`. The Vercel team `AXE Companion OS` contains one
project (`axe-core`) — there is no Companion project. Production is a
self-managed Ubuntu VPS running `next start` behind nginx.

**Consequence:** the eight cron jobs in `vercel.json` have never fired on this
host. Vercel Cron only exists on Vercel. That single fact explains finding #3.

It also explains `chat-health`: `ollama_base_url=http://localhost:11434`,
reachable in 3 ms. Ollama runs on the same box. That works — but it is one
llama3.2 instance serving every user of a paid product.

## 2. CRITICAL — the public anon key reads and writes AXE's memory

`public.memory` has a single policy:

```sql
memory_service_all  FOR ALL  TO PUBLIC  USING (true)  WITH CHECK (true)
```

`TO PUBLIC` includes `anon`. The anon key ships in every browser bundle of all
three apps. Verified against production with nothing but that key:

```
GET /rest/v1/memory?select=*&limit=1
206  content-range: 0-0/17223
[{"id":"10facedd-…","agent":"axe_trader","user_id":"acff7a12-…
```

17,223 memory rows are world-readable. The same policy grants INSERT, UPDATE and
DELETE (not exercised — the policy definition is proof enough).

`public.global_memory` (18,281 rows) is one step behind it: SELECT **and** UPDATE
are granted on `auth.role() = 'authenticated'` with no `user_id` predicate. Any
authenticated session reads and rewrites all of it — including the anonymous
sessions minted in finding #4.

Also open from the Supabase advisors:

| Issue | Count | Effect |
|---|---|---|
| `security_definer_view` (ERROR) | 1 | `public.landing_feedback_public` runs as its owner |
| RLS enabled, **zero policies** | 24 tables | all 15 `intel_*` tables, `axe_convictions`, `core_webhook_secrets`, `shared_memory` — unreadable by the app, so Intel silently renders empty |
| `auth_allow_anonymous_sign_ins` | 98 policies | policies treat anonymous users as full members |
| `function_search_path_mutable` | 5 functions | incl. `axe_plan_is_paid`, `match_axe_knowledge_chunks` |
| `auth_leaked_password_protection` | off | HIBP check disabled on signup |

## 4. CRITICAL — the demo endpoint gives away the product

`POST /api/auth/demo` signs in an anonymous Supabase user and then, with the
service-role key, writes:

```ts
plan: "founder", founder_badge: true, chat_quota_exempt: true
```

No rate limit, no device binding, unlimited repeats. Production already holds the
result:

```
plan=founder  n=118  founder_badge=117  chat_quota_exempt=118
```

118 of 118 entitlement rows are Founder-tier with unlimited AI chat. **Zero paid
subscriptions exist.** The Founder seat counter deliberately excludes
`chat_quota_exempt` rows, so the 100-seat cap is not blown — but nobody has any
reason to pay, and every one of those sessions can reach `global_memory`
(finding #2).

## 6. Migration history has permanently diverged

The repo carries **47** Companion migrations in `supabase/migrations/`.

entries — and every one of them is an AXE Core migration (`axe_core_*`,
`unified_memory`, `computer_workers`, `agent_learning_episodes`, …). **Zero
Companion migrations are recorded.**

They were applied by hand (SQL editor / the `/migrations` copy-paste page). A
`supabase db push` from this repo will now try to replay all 47 from scratch.

Related: `intel-proxy` is deployed from
`file:///Volumes/EagetSSD/TRADING-OS/supabase/functions/intel-proxy/index.ts` and
`livekit-token`/`ai-proxy` from an AXE-CORE path. The deployed Edge code is not
the code in this repo. One Supabase project now backs all three apps with no
schema ownership boundary.

# Addendum — remediation, same day

What was executed, what it disproved in the audit above, and what is left.

## Corrections to this audit

Three claims above did not survive contact with the work.

1. **"`tsc --noEmit` passes."** Wrong. That exit code came from a shell pipeline
   ending in `tail`, not from `tsc`. Measured properly there were **89 type
   errors**. `ignoreBuildErrors: true` is therefore load-bearing, not "pure
   downside" as §7 claimed — and it was hiding two live runtime bugs.
2. **"Intel renders empty because the `intel_*` tables have RLS with no
   policies."** Wrong mechanism. Those tables are read server-side through
   `createServiceRoleSupabaseClient()`, which bypasses RLS. Deny-all is the
   correct posture for them. Intel is empty because the feeds fail and the
   warmup cron never ran. The real RLS casualty was narrower and worse:
   `axe_convictions` and `axe_correlation_snapshots` are read through the
   *caller's* session, so every cache read returned nothing and the GPT-4o
   conviction pass re-ran on every single request.
3. **"Fix Finnhub or wire the Forex Factory fallback" (step 10).** The fallback
   is already wired app-side: `loadEconomicCalendar` tries Finnhub, then
   market-proxy, then Forex Factory (verified returning 81 events). The
   Companion calendar works. Only the Edge function itself fails to degrade,
   which affects Trading OS and AXE Core, not this launch.

A fourth measurement was refined rather than wrong: the 7 Intel feeds returning
`invalid_token` were being tested with the anon key. With a real user JWT they
return **`unknown_action`** — the deployed `intel-proxy` does not contain those
seven handlers at all. The repo does. That is the drift, precisely located.

Also worth recording: of the "135 users", **9 are real accounts**. The other 126
are anonymous demo sessions.

## Deliberately not done

**The MT5 Doctor (`runCloudMt5DoctorAction`, ~635 lines) is broken and I left it
that way.** Its helpers — `safeString`, `minutesSince`, `doctorStep`,
`doctorHeadline`, `overallFromDoctor`, `knownFailureFromStatus`,
`compactMetaError`, `clientGetHistoryDealsRange` — and five timeout constants do
not exist anywhere in the codebase. The types do (`@/types/mt5Doctor`); they were
simply never imported, which is fixed. `Mt5CloudAccountActions.tsx` renders a
button that calls this, so it throws a `ReferenceError` at runtime today.

Writing those helpers means inventing MetaAPI semantics I cannot verify without a
live MT5 account. Doing it blind and calling it done is the failure mode worth
avoiding most, so it is written down here instead. It is a bounded task — one
session with a live MT5 account.

**The 8 migrations applied today were not copied into `supabase/migrations/`.**
The repo's 47 existing files are absent from the live history, so adding files
that *are* in it would create a third source of truth. They are recorded in
`supabase_migrations.schema_migrations` as versions `20260907192131` through
`20260907192754`. Reconciling the 47 (step 16) stays a separate, deliberate act.

**Two inert anonymous auth users** (`4360443a-…`, and one earlier) were created
by probing `/auth/v1/signup` directly to test the intel-proxy hypothesis. They
carry no entitlement and no data. Deleting production auth rows was not worth
doing casually; they are noted so they are not a mystery later.
